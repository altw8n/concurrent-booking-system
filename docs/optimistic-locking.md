# Optimistic locking: реализация и проверка

## Что добавлено

Теперь одну бизнес-операцию выполняют две реализации `BookingStrategy`:

| Файл | Ответственность |
|---|---|
| `booking/service/BookingService.java` | Выбирает стратегию при запуске, управляет ограниченными повторами вне транзакции попытки. |
| `booking/service/NaiveBookingStrategy.java` | Содержит прежний алгоритм без проверки версии. |
| `booking/service/OptimisticBookingStrategy.java` | Выполняет те же проверки и изменения через версионируемую сущность. |
| `seat/entity/OptimisticSeat.java` | Отдельное JPA-представление таблицы `seats` с `@Version`. |
| `seat/repository/OptimisticSeatRepository.java` | Загружает версионируемое место. |
| `exception/BookingConflictException.java` | Представляет окончательный конфликт после исчерпания попыток. |
| `exception/GlobalExceptionHandler.java` | Возвращает HTTP 409 и код `OPTIMISTIC_LOCK_CONFLICT`. |

Сохраняется прежний HTTP-контракт: `POST /api/events/{eventId}/seats/{seatId}/book` с JSON `{"userId": 123}`.

Обе стратегии проверяют идентификатор пользователя, существование мероприятия и пользователя, принадлежность места мероприятию и статус `FREE`. Затем создают `ACTIVE` бронирование и меняют место на `BOOKED`. Используется один и тот же `BookingRepository`, DTO, порядок бизнес-действий и уровень изоляции `READ_COMMITTED`.

Интерфейс появился потому, что теперь действительно существуют две реализации. Дополнительных зависимостей не добавлено. В новых сущностях и стратегиях сохранён уже принятый в проекте Lombok для getters и конструктора; защиту реализуют JPA/Hibernate и PostgreSQL, а не Lombok.

## Почему две сущности для одной таблицы

`Seat` остаётся без `@Version`: иначе исходный naive-сценарий получил бы защиту и перестал бы воспроизводить гонку. `OptimisticSeat` описывает те же столбцы той же таблицы, но её `version` помечена `jakarta.persistence.Version`.

Это целевая особенность исследовательского стенда. В одной транзакции бронирования используется только одно представление строки. Не следует одновременно загружать и изменять оба представления: Hibernate считает их разными сущностями и не синхронизирует их Java-состояние автоматически.

На один запуск приложения выбирается одна стратегия. Эксперименты разных стратегий на одном наборе данных выполняются последовательно, после завершения всех запросов и подготовки свежих данных. Одновременные процессы naive и optimistic, изменяющие одни и те же места, не дают гарантий optimistic locking: naive не соблюдает протокол версий. Прямой SQL и будущие операции изменения мест тоже должны учитываться при формулировке гарантий.

Новая миграция не нужна: `V1` уже создала `version BIGINT NOT NULL DEFAULT 0`. Исторические миграции не изменены, уникальное ограничение активного бронирования не добавлено.

## Что происходит в Spring, Hibernate и PostgreSQL

Цепочка вызовов:

```text
BookingController
  -> BookingService (без собственной транзакции)
    -> Spring proxy выбранной BookingStrategy
      -> начало новой транзакции READ COMMITTED
      -> проверки, SELECT места
      -> INSERT бронирования
      -> изменение Java-объекта места
      -> flush: UPDATE места с проверкой версии
      -> commit либо rollback
    -> результат или исключение
  -> при допустимом конфликте — следующая полная попытка
```

Обе стратегии объявляют `@Transactional(propagation = REQUIRES_NEW, isolation = READ_COMMITTED)`. `REQUIRES_NEW` задаёт отдельную физическую транзакцию каждой попытке, даже если когда-нибудь появится внешний транзакционный вызов. В обычном HTTP-пути внешней транзакции нет: одновременно на попытку требуется одно JDBC-соединение. При добавлении внешней транзакции нужно заново оценить композицию операций и размер пула: внешний вызов может удерживать своё соединение, пока внутренняя транзакция получает другое.

`spring.jpa.open-in-view=false` ограничивает persistence context сервисной транзакцией. Контроллер получает DTO, поэтому ему не нужен доступ к управляемым JPA-сущностям после её завершения. Повторная попытка получает новый persistence context и перечитывает БД.

После загрузки места Hibernate хранит его исходную версию в persistence context. `markBooked()` меняет Java-объект. Dirty checking обнаруживает изменение, а flush отправляет SQL перед фиксацией транзакции. Для `Booking` с `IDENTITY` вставка выполняется раньше, чтобы получить ID; это ещё не означает commit.

Приблизительный SQL успешной попытки, опуская часть столбцов:

```sql
SELECT COUNT(*) FROM events WHERE id = :eventId;
SELECT COUNT(*) FROM users WHERE id = :userId;
SELECT id, event_id, status, version, ... FROM seats WHERE id = :seatId;

INSERT INTO bookings (user_id, seat_id, status, created_at, expires_at)
VALUES (:userId, :seatId, 'ACTIVE', :createdAt, NULL);

UPDATE seats
SET status = 'BOOKED', version = :nextVersion, ...
WHERE id = :seatId AND version = :loadedVersion;
```

Многоточия здесь — пояснение, а не исполняемый SQL. Hibernate также обновляет остальные отображённые поля; точный текст нужно смотреть в SQL-выводе интеграционного теста. У naive в `WHERE` есть только `id`, а автоматического увеличения версии нет.

Если два запроса загрузили версию 0, первый успешный `UPDATE` меняет её на 1. Второй `UPDATE ... WHERE version = 0` после фиксации первого изменяет 0 строк. Hibernate обнаруживает конфликт; Spring переводит исключение в семейство `OptimisticLockingFailureException`.

Ошибка может возникнуть при flush/commit, уже после исполнения тела метода стратегии. Поэтому перехват находится в вызывающем `BookingService`, снаружи транзакционного proxy. Проигравшая транзакция откатывается целиком, включая ранее выполненный `INSERT bookings`.

При чтении нет явного `SELECT FOR UPDATE`. При `UPDATE` PostgreSQL всё равно блокирует изменяемую строку, и конкурирующий `UPDATE` может ждать. Блокировки удерживаются до завершения транзакции. Optimistic locking не означает полного отсутствия блокировок и ожиданий.

## Исходы и повторы

| Ситуация | Результат |
|---|---|
| Место свободно, версия не изменилась | HTTP 201, одно активное бронирование, версия увеличена на 1. |
| При чтении место уже `BOOKED` | HTTP 409, `SEAT_ALREADY_BOOKED`; повтора нет. |
| Версия изменилась после чтения, попытки закончились | HTTP 409, `OPTIMISTIC_LOCK_CONFLICT`. |
| Версия изменилась, повтор разрешён | Полный повтор в новой транзакции; состояние места читается заново. |
| Другая ошибка | Не повторяется этим механизмом. |

`booking.optimistic.max-retries` — число **дополнительных** попыток, от 0 до 10. Значение 0 означает одну попытку, 1 — максимум две. По умолчанию повторы выключены, чтобы сначала исследовать сам механизм. Они выполняются сразу, без отдельной библиотеки и без задержки; вариант с backoff сейчас не реализован.

Для единственного места после проигранного конфликта повтор обычно обнаружит `BOOKED` и вернёт бизнес-отказ. Повторы не создают дополнительное свободное место и не гарантируют успех. Серии с повторами и без них нужно измерять отдельно. Настройка повторов optimistic не применяется к naive.

При корректном начальном состоянии и соблюдении протокола всеми операциями записи optimistic-стратегия предотвращает появление второго активного бронирования в исследуемой операции. Она не устраняет уже существующие нарушения и не является ограничением целостности на уровне всей БД.

## Запуск

Для приложения нужна PostgreSQL из Compose:

```bash
docker compose up -d
./gradlew bootRun --args='--booking.strategy=optimistic'
```

С одним разрешённым повтором:

```bash
./gradlew bootRun --args='--booking.strategy=optimistic --booking.optimistic.max-retries=1'
```

Без параметров сохранён `booking.strategy=naive`. Неизвестная стратегия и недопустимое количество повторов приводят к ошибке запуска, а не к молчаливому выбору другого алгоритма.

## Тесты

`OptimisticBookingIntegrationTest` использует настоящую PostgreSQL 17 через Testcontainers, без внешней транзакции теста. Проверяет:

1. Бронирование и увеличение уже существующей версии 41 до 42, отказ повторному последовательному бронированию.
2. Два одновременных чтения версии 0: один победитель, один конфликт, в БД остаётся только одно бронирование.
3. Один retry: три разные физические транзакции PostgreSQL, повторное чтение версии 1, отказ `SEAT_ALREADY_BOOKED`, отсутствие лишних записей.
4. Контролируемый сбой изменения места: откатываются бронирование и изменение версии; следующая попытка после снятия тестового ограничения успешна.
5. Те же проверки запроса, что у naive, без записи при ошибке.
6. Одновременное бронирование разных мест: оба запроса успешны, версии независимы.

Гонка синхронизирована `CyclicBarrier` после чтения места. При повторе барьер больше не применяется. Для проверки границ транзакций тестовый код получает `pg_current_xact_id()` через то же транзакционное JDBC-соединение. Этот диагностический SQL и барьер отсутствуют в приложении и не подходят для измерения производительности.

`BookingServiceTest` проверяет выбор стратегии, ограничение числа попыток, успешный повтор и отсутствие повторов для бизнес-отказа и неожиданного сбоя. Прежние семь unit-тестов бизнес-правил перенесены в `NaiveBookingStrategyTest`. `BookingControllerTest` дополнен проверкой отдельного кода конфликта. Прежние тесты гонки и отката явно выбирают naive.

Полный набор — **30 тестов**. Testcontainers поднимает собственные контейнеры; запуск PostgreSQL из Compose для тестов не требуется, но Docker daemon должен быть доступен.

```bash
./gradlew test --rerun-tasks
./gradlew test --tests '*OptimisticBookingIntegrationTest' --rerun-tasks
```

Точный SQL optimistic-обновления виден в выводе теста и в `build/test-results/test/TEST-com.example.concurrent_booking_system.booking.service.OptimisticBookingIntegrationTest.xml`. Отчёт HTML: `build/reports/tests/test/index.html`.

### Проверка в среде агента

- Все 34 основных Java-файла и 7 тестовых Java-файлов скомпилированы JDK 21 с зависимостями из локального кеша и обработчиком Lombok.
- Hibernate 7.4.5 успешно построил SessionFactory с обеими сущностями без подключения к БД; метамодель подтверждает наличие версии у `OptimisticSeat` и её отсутствие у `Seat`. Это проверка отображений, а не поведения PostgreSQL.
- Через JUnit Platform 6.0.3 вне Gradle успешно выполнен **21 тест** сервиса, naive-алгоритма и контроллера; использовался Mockito javaagent.
- Gradle Wrapper не смог создать lock-файл в доступном только для чтения `~/.gradle`; доступ к Docker API также отклонён.
- Отдельная попытка выполнения PostgreSQL-тестов остановилась до тестовых методов: Testcontainers не смог подключиться к `/var/run/docker.sock`, корневая ошибка `SocketException: Operation not permitted`. Успешное выполнение новых PostgreSQL-тестов пока не подтверждено. Старые XML-отчёты 14 тестов относятся к предыдущему коммиту и не подтверждают эту реализацию.
