# Просмотр и отмена бронирований

## Назначение модуля

После пяти способов бронирования добавлены просмотр истории пользователя и общая операция отмены. Пользовательский сценарий теперь включает бронирование, просмотр, отмену и новое бронирование освободившегося места. Отмена не удаляет Booking и не переиспользует его ID: новая бронь — новая запись, старая остаётся `CANCELLED`.

Основные файлы:

- `booking/controller/BookingManagementController.java`: HTTP-маршруты и передача параметров сервису.
- `booking/service/BookingManagementService.java`: проверки, транзакции чтения и отмены.
- `booking/repository/BookingRepository.java`: упорядоченный список и условная отмена.
- `seat/repository/SeatRepository.java`: существующая блокировка строки и новое освобождение места.
- `exception/BookingNotFoundException.java`, `BookingAccessDeniedException.java`, `BookingCancellationTimeoutException.java`: разные ожидаемые исходы.
- `exception/GlobalExceptionHandler.java`: преобразование ожидаемых ошибок в единый JSON.
- `application.properties`: независимый лимит ожидания блокировки при отмене.

Схема и пять алгоритмов создания бронирования не изменены. `expiresAt` остаётся nullable-полем для будущего расширения; автоматического истечения брони нет.

## HTTP API

### Список пользователя

```http
GET /api/users/1/bookings
```

Возвращает HTTP 200 и массив `BookingResponseDto`, включая `ACTIVE` и `CANCELLED`. Сначала идут новые записи: `created_at DESC, id DESC`. ID делает порядок однозначным при одинаковом времени создания. Для существующего пользователя без бронирований возвращается `[]`; для отсутствующего — 404 `USER_NOT_FOUND`. Неположительный ID — 400 `INVALID_REQUEST`.

Это история бронирований с их текущими статусами, а не журнал каждого изменения: времени отмены и отдельной таблицы аудита пока нет. Список без пагинации подходит для текущего учебного объёма; большое число записей потребует отдельного ограничения выдачи.

### Отмена

```http
DELETE /api/bookings/10?userId=1
```

Успех — HTTP 204 без тела. Первый запрос меняет `ACTIVE` на `CANCELLED`; повтор от того же пользователя также возвращает 204 и больше ничего не меняет. Такая повторяемость важна, например, если клиент потерял ответ и отправил запрос снова.

`userId` обязателен и проверяется на принадлежность бронированию. Это тестовый идентификатор пользователя, который клиент задаёт самостоятельно. Авторизации в проекте нет: проверка принадлежности не подтверждает личность отправителя. Аналогичное ограничение есть у существующего POST бронирования.

| Ситуация | HTTP | Код JSON-ошибки |
| --- | --- | --- |
| Отсутствующее бронирование | 404 | `BOOKING_NOT_FOUND` |
| Отсутствующий пользователь | 404 | `USER_NOT_FOUND` |
| Бронирование принадлежит другому существующему пользователю, включая уже отменённое | 403 | `BOOKING_ACCESS_DENIED` |
| Неположительный ID, отсутствующий `userId`, неверный тип параметра | 400 | `INVALID_REQUEST` |
| Истёк срок ожидания блокировки БД | 503 | `BOOKING_CANCELLATION_TIMEOUT` |

Неожиданные SQL-ошибки не превращаются в «место занято» или успешную отмену. Отмена не имеет автоматических повторов.

## Транзакция в Spring

Контроллер вызывает публичный метод `BookingManagementService.cancelBooking()` через Spring proxy. Его `@Transactional(REQUIRES_NEW, READ_COMMITTED)` открывает отдельную транзакцию до входа в метод; внешняя транзакция, если есть, приостанавливается. Все SQL-команды отмены используют одно JDBC-соединение и один persistence context.

Транзакция завершается после выхода из метода через proxy. HTTP 204 формируется после успешного commit. Если SQL или commit завершается ошибкой, изменения Booking и Seat откатываются вместе. Прикладной код не отправляет внешние запросы и не ожидает действий пользователя внутри транзакции.

У просмотра списка отдельный `@Transactional(readOnly = true)`: DTO собираются внутри транзакции, JPA-сущности контроллеру не передаются. `readOnly` задаёт режим работы транзакции/ORM, а не права пользователя на чтение чужих данных.

## Приблизительный SQL отмены

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

SELECT count(*) FROM users WHERE id = :userId;
SELECT * FROM bookings WHERE id = :bookingId;
-- Java validates ownership and returns early if already CANCELLED.

SELECT set_config('lock_timeout', '2000ms', true);
SELECT * FROM seats WHERE id = :seatId FOR NO KEY UPDATE;

UPDATE bookings SET status = 'CANCELLED'
WHERE id = :bookingId AND status = 'ACTIVE';

-- Execute only if the previous UPDATE affected one row.
UPDATE seats SET status = 'FREE', version = version + 1
WHERE id = :seatId
  AND NOT EXISTS (
      SELECT 1 FROM bookings WHERE seat_id = :seatId AND status = 'ACTIVE'
  );

COMMIT;
```

Для блокировки повторно используется `SeatRepository.findByIdForUpdate()` с `@Lock(PESSIMISTIC_WRITE)`. Диалект PostgreSQL текущего Hibernate использует `FOR NO KEY UPDATE`. Сначала блокируется место, затем изменяется Booking. Все отмены придерживаются этого порядка; при расширении операций над несколькими местами порядок захвата придётся определить отдельно.

Настройка `booking.cancellation.lock-timeout-ms=2000` ограничивает ожидание каждого получения блокировки и должна быть положительной. Это не общий тайм-аут HTTP-запроса. `set_config(..., true)` действует локально в транзакции и не оставляет настройку следующему пользователю соединения из пула. Только SQLSTATE `55P03` преобразуется в ошибку тайм-аута отмены; deadlock `40P01` отдельно не повторяется и не маскируется как timeout.

## Зачем нужны блокировка и условие ACTIVE

Начальное чтение Booking служит для поиска места и проверки владельца. Если две отмены прочитали `ACTIVE`, одна может ждать блокировку места, пока другая завершится. Её Java-объект после ожидания всё ещё содержит старый статус.

Поэтому отмена не полагается на это старое чтение. Новый SQL `UPDATE ... WHERE status = 'ACTIVE'` проверяет текущее состояние БД. Одна отмена изменит строку и освободит место; вторая получит ноль изменённых строк и пропустит освобождение. Последовательный повтор для уже `CANCELLED` завершается ещё раньше, без блокировки места.

Если после первой отмены появилась новая бронь, повторная отмена старой не изменяет ни статус места, ни его версию. Именно этого нельзя добиться безусловным присваиванием `seat.status = FREE` при каждом DELETE.

`NOT EXISTS` дополнительно не позволяет освободить место, пока у него остаётся другое активное бронирование. Это важно для тестовых данных, уже испорченных naive-гонкой: отмена одной из двух броней не должна объявить занятое другой бронью место свободным. Сам naive-алгоритм остаётся незащищённым и по-прежнему может создавать дубли.

## Hibernate и версия места

В начале операции Booking и Seat читаются как управляемые сущности. Их Java-поля сервис не меняет: запись производится явными bulk SQL-командами. У обоих `@Modifying` включены `flushAutomatically` и `clearAutomatically`: ожидающие изменения сбрасываются перед SQL, затем persistence context очищается, чтобы в нём не оставались старые статусы и версии. Очистка контекста не освобождает блокировки PostgreSQL: они сохраняются до завершения транзакции.

Освобождение явно выполняет `version = version + 1`. У обычной сущности Seat нет `@Version`, поэтому автоматического увеличения Hibernate здесь не будет. Явное увеличение нужно для совместимости с optimistic-бронированием: транзакция, прочитавшая `FREE/version=0` до цикла «заняли → отменили», не должна успешно записать своё старое состояние после этого цикла.

В optimistic-режиме новое бронирование увеличивает версию до 1, отмена — до 2, а старая транзакция пытается выполнить `UPDATE ... WHERE version = 0`. Такой UPDATE не находит строку; её INSERT бронирования откатывается. Обычное повторное DELETE версию не увеличивает.

В атомарном и pessimistic-режимах при бронировании версия по-прежнему не увеличивается, но при реальном освобождении места увеличивается общей операцией отмены. Сравнение стратегий создания брони остаётся отдельной задачей; версия не добавлена в WHERE их запросов.

## Как отмена взаимодействует с бронированием

Отмена одинакова для всех выбранных стратегий, но исход параллельного запроса зависит от момента чтения:

- Pessimistic-запрос блокировки места может дождаться commit отмены и затем прочитать `FREE`.
- Обычный SELECT optimistic/serializable и условный atomic UPDATE могут увидеть ещё зафиксированное `BOOKED` и вернуть отказ до завершения отмены. Клиент сможет сделать новый запрос после её завершения.
- Уже начавшаяся optimistic-попытка со старой версией обнаружит конфликт; serializable-попытка со старым снимком может получить `40001` и обрабатывается существующей политикой повторов.

Не требуется, чтобы любой запрос, пересёкшийся по времени с отменой, успешно бронировал место. Требуется, чтобы итоговое состояние и успешные ответы соответствовали допустимому порядку операций.

Обоснование относится к одной выбранной стратегии бронирования для одного места и общей операции отмены. Смешивание разных способов создания брони над одним местом, прямые SQL-записи и будущие групповые операции требуют отдельного анализа. Общая отмена на `READ_COMMITTED` также не означает, что все транзакции приложения работают на `SERIALIZABLE`.

Первую нагрузочную серию следует проводить над операцией создания бронирования, отдельно от отмены. Включение отмен в измеряемый поток добавляет другую нагрузку и требует отдельной методики.

## Проверки

Новые unit/MockMvc-тесты: `BookingManagementServiceTest` (9) и `BookingManagementControllerTest` (6). Проверяются ошибки, права на операцию в рамках тестового userId, условная отмена после ожидания, порядок блокировки/записи и HTTP-контракт.

`BookingLifecycleIntegrationTest` использует PostgreSQL 17 через Testcontainers, настоящие Spring transaction proxy и MockMvc со всем WebApplicationContext. В классе 8 обычных тестов и 2 параметризованных по четырём защищённым стратегиям — **16 выполнений при успешном запуске**:

- Жизненный цикл и повторная отмена старой брони после нового бронирования — для каждой защищённой стратегии.
- Бронирование во время незавершённой отмены — для каждой защищённой стратегии.
- История только нужного пользователя, оба статуса и стабильная сортировка.
- Полный сценарий через реальные HTTP-контроллеры и БД; ожидаемые HTTP-ошибки без изменения данных.
- Две отмены, обе прочитавшие ACTIVE: одно освобождение и одно увеличение версии.
- Старая optimistic-попытка до цикла бронирования/отмены: конфликт и откат её INSERT.
- Искусственная ошибка освобождения: CHECK применяется только к месту текущего теста, все изменения откатываются.
- Настоящий lock timeout: прежняя бронь остаётся ACTIVE; после снятия блокировки новая отмена успешна.
- Дубли ACTIVE из naive-данных: место освобождается после отмены последней активной брони.

Порядок потоков задаётся барьером и latch в тестовых обёртках репозиториев; ожидание блокировки подтверждается через `pg_blocking_pids()`. Эти обёртки не входят в рабочее приложение. Тесты проверяют данные после завершения транзакций; это не замеры производительности. MockMvc проверяет обработку HTTP без открытия сетевого порта.

На момент реализации все 44 основных и 15 тестовых Java-файлов скомпилированы JDK 21, все **55 unit/MockMvc-тестов прошли** отдельно через JUnit Platform с локальными зависимостями. Новые PostgreSQL-проверки пока не выполнены: Wrapper не может создать lock-файл в read-only `~/.gradle`, а Testcontainers не имеет доступа к Docker socket. Сохранённые 69 успешных XML-отчётов относятся к предыдущему serializable-коммиту `6e7d4e2`.

Ожидаемый полный набор после этого шага — **100 выполнений тестов: 55 unit/MockMvc и 45 с PostgreSQL**. Число включает развёртывание параметризованных тестов; до запуска их четыре варианта не обязательно видны как четыре отдельных теста в отчёте discovery.

## Самостоятельная проверка

При доступном Docker:

```bash
./gradlew test --tests '*BookingLifecycleIntegrationTest' --rerun-tasks
./gradlew test --rerun-tasks
```

Compose-БД не нужна для Testcontainers. Для ручных HTTP-запросов запустить Compose и приложение, выбрать существующие user/event/seat ID:

```bash
docker compose up -d
./gradlew bootRun --args='--booking.strategy=optimistic'
```

Пример для уже существующего пользователя 1 и бронирования 10:

```bash
curl http://localhost:8080/api/users/1/bookings
curl -i -X DELETE 'http://localhost:8080/api/bookings/10?userId=1'
```

После успешного полного набора тестов сообщение коммита:

```text
feat: add booking history and concurrency-safe cancellation
```

Семантика блокировок и снимков: [PostgreSQL 17: Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html), [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED). Детали выбранного протокола отмены и его границы описаны выше; общие свойства PostgreSQL сами по себе не доказывают корректность произвольного Java-кода.
