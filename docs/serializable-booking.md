# SERIALIZABLE booking

## Зачем нужна эта реализация

`SerializableBookingStrategy` выполняет ту же операцию, что и naive: проверяет пользователя и мероприятие, читает место, проверяет `FREE`, создаёт `ACTIVE` бронирование и меняет место на `BOOKED`. Отличие — уровень изоляции всей транзакции PostgreSQL: `SERIALIZABLE` вместо `READ_COMMITTED`.

Уровень изоляции задаёт допустимое взаимодействие параллельных транзакций. При `SERIALIZABLE` результат успешно завершившихся транзакций соответствует некоторому последовательному порядку их выполнения. PostgreSQL продолжает выполнять их параллельно, но может отменять конфликтующие попытки. Это свойство не превращает неверный последовательный алгоритм в правильный: наши проверки и изменение места всё равно необходимы.

Для сравнения механизмов здесь нет `@Version`, предварительного `SELECT FOR UPDATE` или условного UPDATE по `status`. Используется обычная сущность `Seat`; существующее поле `version` не увеличивается. Миграции, ограничения БД и naive-реализация не меняются.

## Spring: граница транзакции и повторы

Публичный метод стратегии объявлен так:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, isolation = Isolation.SERIALIZABLE)
public BookingResponseDto bookSeat(Long eventId, Long seatId, Long userId)
```

HTTP-контроллер вызывает `BookingService`. У него нет собственной транзакции: он выбирает реализацию и вызывает её через Spring proxy. Перед входом в метод стратегии proxy открывает новую транзакцию через JPA transaction manager и настраивает JDBC connection. Запросы этой попытки используют одно соединение и один persistence context. `REQUIRES_NEW` также приостанавливает внешнюю транзакцию, если вызывающий код её открыл.

Метод стратегии возвращает DTO, затем proxy завершает транзакцию. Только после успешного commit результат попадает в `BookingService`. Исключение при SQL или commit сначала завершает неудачную попытку с откатом, а затем выходит в `BookingService`.

Поэтому цикл повторов находится снаружи стратегии. Новый вызов proxy создаёт новую физическую транзакцию и новый persistence context; место читается заново. Повтор одного UPDATE внутри уже отменённой транзакции не используется.

Настройки независимы:

```properties
booking.strategy=serializable
booking.serializable.max-retries=0
```

Значение `0` означает одну исходную попытку, `1` — максимум две попытки, `2` — максимум три. Допустим диапазон 0–10. По умолчанию повторов нет: это позволяет сначала измерять механизм без влияния retry. Настройка `booking.optimistic.max-retries` на эту стратегию не влияет; настройка serializable не меняет остальные стратегии.

Повторы немедленные и ограниченные, без backoff. Такая политика сама является параметром будущего эксперимента. При высокой конкуренции она может увеличивать нагрузку; больше повторов не означает больше успешных бронирований.

## Hibernate: когда выполняется SQL

Чтение возвращает управляемую сущность `Seat`. Hibernate сохраняет её исходное состояние в persistence context. Вызов `markBooked()` изменяет Java-объект; dirty checking обнаруживает это изменение при flush.

У `Booking` используется `IDENTITY`, поэтому Hibernate обычно выполняет INSERT во время `save()`, чтобы получить сгенерированный ID. UPDATE места выполняется при flush, в том числе перед commit. INSERT и UPDATE остаются частью одной транзакции независимо от момента отправки SQL.

Приблизительная последовательность на уровне БД (служебные запросы и полный список столбцов сокращены):

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*) FROM events WHERE id = :eventId;
SELECT count(*) FROM users WHERE id = :userId;
SELECT * FROM seats WHERE id = :seatId;
-- Java checks event_id and status = 'FREE'.

INSERT INTO bookings (user_id, seat_id, status, created_at, expires_at)
VALUES (:userId, :seatId, 'ACTIVE', :createdAt, NULL);

UPDATE seats
SET event_id = :eventId, row_number = :rowNumber, seat_number = :seatNumber,
    status = 'BOOKED', price = :price, version = :version
WHERE id = :seatId;

COMMIT;
```

Spring задаёт изоляцию через JDBC; отдельная текстовая команда `BEGIN ISOLATION LEVEL ...` в логе Hibernate может отсутствовать. Фактическая изоляция проверяется тестом через `SHOW transaction_isolation` на соединении текущей попытки.

UPDATE берёт обычную блокировку строки до завершения транзакции; INSERT также участвует в проверках внешних ключей и других ограничений. Отсутствие явного `FOR UPDATE` не означает отсутствие блокировок вообще.

## Что происходит при конфликте

Представим такой допустимый порядок:

1. Транзакции A и B получают снимки, в которых место `FREE`.
2. A сохраняет бронирование, меняет место и делает commit.
3. B пытается изменить место на основе прежнего снимка.
4. PostgreSQL отменяет B с SQLSTATE `40001`; её INSERT также откатывается.

В PostgreSQL этот уровень построен на снимках и отслеживании зависимостей чтения/записи (Serializable Snapshot Isolation, SSI). Он способен обнаруживать и более сложные опасные взаимодействия нескольких строк. Наш основной тест с одним местом проверяет конфликт обновления общей строки, а не весь спектр SSI. Подобный конфликт возможен и в PostgreSQL `REPEATABLE READ`: этот тест не доказывает уникальность SERIALIZABLE.

Не следует ожидать, что SERIALIZABLE всегда завершается без ожиданий или отменяет только запросы к одному месту. Обычные блокировки остаются, а отслеживание чтений может быть достаточно грубым, чтобы отменять и логически независимые операции. Количество конфликтов и стоимость повторов предстоит измерять.

## Классификация ошибок

`BookingService` проверяет SQLSTATE в цепочке причин исключения: форма Spring/Hibernate-обёртки при запросе и при commit может различаться. Повторяется только `40001` и только при выбранной serializable-стратегии.

| Ситуация | Поведение |
| --- | --- |
| `40001`, попытки ещё доступны | Повтор всей операции в новой транзакции |
| `40001`, лимит исчерпан | `BookingSerializationException`, HTTP 409, `SERIALIZATION_FAILURE` |
| Новая попытка видит `BOOKED` | HTTP 409, `SEAT_ALREADY_BOOKED`, без дальнейшего повтора |
| Некорректный запрос / отсутствующая сущность | Прежняя бизнес-ошибка, без повтора |
| Deadlock `40P01`, lock timeout `55P03`, нарушение CHECK `23514` | Не считаются serialization failure и автоматически здесь не повторяются |
| Неожиданный сбой | Передаётся вызывающему коду, без повтора |

Автоматический retry не гарантирует победу. Если A уже заняла место, корректный результат повторной попытки B — отказ, а не второе бронирование. Конкретный победитель не гарантируется. Откат не возвращает значения sequence: пропуски в ID после неудачных попыток допустимы.

Гарантии сравниваются при одной выбранной стратегии на запуск приложения. Смешивание незащищённых писателей naive с защищёнными писателями, прямое изменение БД или несогласованная будущая отмена требуют отдельного анализа. Уникального ограничения на активные бронирования пока нет, чтобы сохранить исследовательский naive-контроль.

## Тесты этого шага

`SerializableBookingIntegrationTest` использует настоящий PostgreSQL 17 через Testcontainers, без внешней тестовой транзакции:

1. Успех и последовательный отказ для занятого места; `version` не увеличивается.
2. Две транзакции читают `FREE`: одна успешна, другая получает настоящий `40001`. В БД ровно одно бронирование и оно `ACTIVE`, место `BOOKED`.
3. При одном разрешённом retry проигравшая операция получает новую транзакцию и видит `BOOKED`. Проверяются три разных PostgreSQL transaction ID и фактический `SERIALIZABLE` у всех попыток.
4. Временный CHECK запрещает UPDATE только тестового места. Проверяется SQLSTATE `23514`, откат INSERT, сохранение `FREE` и успешная следующая операция после удаления CHECK. Ранее созданное бронирование другого места сохраняется.
5. Те же проверки входных данных, отсутствующих сущностей и принадлежности места мероприятию; ошибочные операции не создают бронирования.

Барьер стоит после чтения места обеими транзакциями. Затем latch разрешает второй записи продолжиться после commit первой: обе уже прочитали `FREE`, а retry гарантированно начинается после победителя. Это один намеренно заданный порядок выполнения, позволяющий воспроизводимо проверить конфликт и свежий снимок, без `Thread.sleep`. Это проверка корректности, а не нагрузочный замер. Синхронизация добавляется только тестовой обёрткой репозитория.

Unit-тесты проверяют выбор стратегии, ограничение числа попыток, независимость настроек, вложенную ошибку commit и отсутствие повторов для других исходов. MockMvc проверяет отдельный HTTP-код ошибки сериализации. Существующий optimistic-тест обновлён только под расширенный конструктор сервиса.

## Запуск и состояние проверки

Из обычного терминала с доступом к Docker:

```bash
./gradlew test --tests '*SerializableBookingIntegrationTest' --rerun-tasks
./gradlew test --rerun-tasks
```

Тестовые контейнеры создаются автоматически; Compose-БД для них запускать не требуется. Для ручной работы приложения нужна Compose-БД:

```bash
docker compose up -d
./gradlew bootRun --args='--booking.strategy=serializable --booking.serializable.max-retries=1'
```

Состояние на момент реализации: все 39 основных и 12 тестовых Java-файлов компилируются JDK 21; все 40 unit/MockMvc-тестов прошли отдельно через JUnit Platform с локально закешированными зависимостями. Полный набор содержит 69 тестов: 40 unit/MockMvc и 29 с PostgreSQL. PostgreSQL-проверки нового шага пока не подтверждены: в среде агента Wrapper не может записать lock-файл в `~/.gradle`, а Testcontainers не получает доступ к Docker socket. Прежние сохранённые 56 успешных тестов относятся к atomic-коммиту `bad4a2c`, а не к новым изменениям. История проверки указана в `ROADMAP.md`.
