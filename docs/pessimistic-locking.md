# Pessimistic locking: бронирование с блокировкой строки

## Назначение и границы шага

Добавлена третья реализация одной операции бронирования — `PessimisticBookingStrategy`. Она захватывает блокировку строки места **до проверки FREE**. Конкурирующий запрос к тому же месту ждёт завершения первой транзакции, затем проверяет актуальный статус.

Модули naive и optimistic сохраняются. Новых библиотек, сущностей, таблиц и миграций не добавлено. Приложение по-прежнему один модульный монолит с PostgreSQL. Производительность пока не измеряется: этот этап закрепляет корректность и поведение ожиданий.

## Что делает Spring

Контроллер вызывает `BookingService`, который сам не открывает транзакцию. Он делегирует работу выбранной стратегии через Spring proxy.

`PessimisticBookingStrategy.bookSeat()` объявлен с:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, isolation = Isolation.READ_COMMITTED)
```

Перед выполнением тела метода Spring начинает отдельную физическую транзакцию. Чтение, настройка ожидания, вставка бронирования и изменение места используют одно JDBC-соединение. `JpaTransactionManager` связывает его с текущим потоком; `JdbcTemplate` получает то же транзакционное соединение, что и Hibernate.

После нормального завершения тела метода Hibernate выполняет flush, затем транзакция фиксируется. При runtime-ошибке она откатывается. Блокировка не заканчивается при возврате из метода репозитория: она удерживается до commit/rollback всей операции бронирования. Ответ об успехе возвращается контроллеру после успешного commit.

`spring.jpa.open-in-view=false` уже настроен предыдущим шагом. Управляемые сущности остаются внутри сервисной транзакции, HTTP получает DTO.

## Что делает JPA/Hibernate

Метод `SeatRepository.findByIdForUpdate()` использует:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Аннотация передаёт режим блокировки провайдеру JPA. Hibernate формирует блокирующий SQL, а саму блокировку предоставляет PostgreSQL. Это не Java-monitor и не `synchronized`: координация работает между соединениями и процессами, обращающимися к этой БД.

Загруженный `Seat` отслеживается в persistence context. После проверки `FREE` создаётся `Booking`, затем `seat.markBooked()` меняет Java-объект. Dirty checking приводит к `UPDATE seats` при flush. Отдельный `save(seat)` не нужен.

У `Seat` нет `@Version`, поэтому эта реализация не использует optimistic locking и не увеличивает версию. Защита здесь обеспечивается порядком: получить блокировку → проверить статус → изменить данные → завершить транзакцию.

## SQL и PostgreSQL

Приблизительная последовательность:

```sql
BEGIN;
-- READ COMMITTED задаётся через Spring/JDBC.
SELECT COUNT(*) FROM events WHERE id = :eventId;
SELECT COUNT(*) FROM users WHERE id = :userId;

SELECT set_config('lock_timeout', '2000ms', true);

SELECT id, event_id, status, version, ...
FROM seats
WHERE id = :seatId
FOR NO KEY UPDATE;

-- Проверка FREE выполняется в Java после получения строки и блокировки.
INSERT INTO bookings (...) VALUES (...);
UPDATE seats SET status = 'BOOKED', ... WHERE id = :seatId;
COMMIT;
```

Многоточия пояснительные, это не готовый исполняемый скрипт. `BEGIN`/`COMMIT` показаны как границы транзакции, а не как SQL из контроллера. Конкретные значения передаются параметрами.

В локальном исходнике Hibernate 7.4.5 `PostgreSQLDialect.getForUpdateString()` возвращает `for no key update`, поэтому `PESSIMISTIC_WRITE` не обязательно буквально даёт `FOR UPDATE`. Для изменения статуса одного места эта блокировка предотвращает конфликтующее изменение и получение такой же блокировки другим запросом. Точный SQL нужно сверить с выводом PostgreSQL-теста; изучение исходника диалекта не заменяет его выполнение.

Обычный `SELECT` списка мест не обязан ждать эту блокировку. Другой блокирующий запрос к тому же месту ждёт, а операции с другими строками могут продолжаться. Автоматические блокировки таблицы также существуют; это не означает эксклюзивную блокировку всей таблицы мест.

Если первая транзакция фиксирует бронирование, ожидающая вторая при READ COMMITTED получает строку со статусом `BOOKED` и возвращает бизнес-отказ. Если первая откатывается, место остаётся свободным и второй запрос может его забронировать.

## Ограничение ожидания

Использован PostgreSQL `lock_timeout` с транзакционной областью действия:

```sql
SELECT set_config('lock_timeout', :timeout, true);
```

`true` соответствует локальной настройке: после commit или rollback восстанавливается прежнее значение. Настройка не должна попадать в следующий запрос, которому пул выдаст это соединение.

Это предел **каждого ожидания блокировки после установки настройки**, а не максимальное время всего HTTP-запроса. Он не ограничивает ожидание свободного JDBC-соединения и не является `statement_timeout` или общим тайм-аутом транзакции. Проверки существования пользователя и мероприятия выполняются до его установки.

По умолчанию ожидание 2000 мс; конфигурация должна быть положительным целым числом. Ноль не разрешён, поскольку PostgreSQL трактует его как отключение тайм-аута.

Для получения строки места Spring переводит Hibernate-ошибку в семейство `PessimisticLockingFailureException`. Стратегия проверяет SQLSTATE в цепочке причин, а не язык текста ошибки:

| Ситуация | Результат |
|---|---|
| Бронирование успешно | HTTP 201. |
| Получена строка с `BOOKED` | HTTP 409, `SEAT_ALREADY_BOOKED`. |
| Получение блокировки места завершилось `55P03` | Откат, HTTP 503, `PESSIMISTIC_LOCK_TIMEOUT`. |
| Другая ошибка, например deadlock `40P01` | Откат; не выдаётся за тайм-аут. Отдельная HTTP-классификация deadlock в этом шаге не добавляется. |

В этом пути не используются `NOWAIT` и `SKIP LOCKED`: запрос должен ждать, а отсутствие блокировки не должно выглядеть как отсутствие места. `55P03` в общем случае означает `lock_not_available`, а в нашей конфигурации соответствует истечению ожидания при захвате блокировки. Специальная классификация находится вокруг запроса блокировки места; другие SQL-сбои не маскируются этим кодом.

Автоматических повторов для pessimistic нет. Параметр `booking.optimistic.max-retries` к ней не применяется.

## Что остаётся возможным

- При высокой конкуренции запросы ждут, занимают JDBC-соединения и могут получать тайм-ауты. Корректность не означает высокую пропускную способность.
- Длительные транзакции увеличивают очередь ожидания. Внешних HTTP-вызовов в транзакции нет.
- Взаимные блокировки возможны при циклическом захвате разных ресурсов. Мы не добавляем многоместные операции ради искусственного deadlock; при расширении операции нужно согласовывать порядок захвата блокировок.
- Гарантии относятся к этой операции при корректном исходном состоянии и согласованных операциях записи. Нельзя одновременно запускать naive и защищённую стратегию над теми же местами и считать весь стенд защищённым. Уже существующие дубликаты не исправляются.

Один запуск приложения использует одну стратегию. Сравнения выполняются на свежих данных после завершения запросов предыдущей серии. Дополнительный запрос настройки `lock_timeout` входит в стоимость этой реализации и должен учитываться в будущих HTTP-измерениях.

## Проверки

Семь PostgreSQL-тестов проверяют:

1. Успешное бронирование и отказ последовательному повтору; версия не меняется.
2. Два запроса к одному месту: второй действительно ждёт, после commit первого получает `SEAT_ALREADY_BOOKED`; в БД ровно одно активное бронирование.
3. После rollback первого ожидающий второй успешно бронирует место.
4. Два разных места могут одновременно удерживаться разными транзакциями и успешно бронироваться.
5. При удерживаемой внешней блокировке происходит тайм-аут `55P03`, нет частичных записей; после освобождения места новая попытка успешна. Проверяются настройки всех четырёх соединений тестового пула после отката и успешного commit.
6. При контролируемом SQL-сбое изменения места откатывается вставка бронирования и освобождается блокировка.
7. Ошибки входных данных и поиска сущностей не оставляют изменений.

Тестовый перехватчик приостанавливает первый запрос **после реального получения блокировки** через `CountDownLatch`. Основной тест проверяет `pg_stat_activity` и `pg_blocking_pids()`, затем освобождает первый запрос. Короткий polling наблюдает состояние БД, а не пытается создать гонку задержкой. Для разных мест используется барьер; для одного места такой барьер после чтения не используется, поскольку второй запрос не может пройти блокировку.

Все эти перехватчики и диагностические запросы существуют только в тестах. На самих тестах нет `@Transactional`: проверяется реальный commit/rollback сервисной операции.

## Запуск и коммит

Для приложения:

```bash
docker compose up -d
./gradlew bootRun --args='--booking.strategy=pessimistic'
```

С другим пределом ожидания:

```bash
./gradlew bootRun --args='--booking.strategy=pessimistic --booking.pessimistic.lock-timeout-ms=1000'
```

Без параметра стратегии остаётся naive. HTTP API не изменился.

Полный набор теперь содержит **43 теста в 9 классах**: 27 unit/MockMvc и 16 PostgreSQL-тестов. Для Testcontainers нужен доступный Docker daemon; БД из Compose для тестов не требуется.

```bash
./gradlew test --rerun-tasks
./gradlew test --tests '*PessimisticBookingIntegrationTest' --rerun-tasks
```

Тест тайм-аута намеренно ожидает около пяти секунд — это настройка тестового контекста, не зависание. SQL и диагностические сообщения находятся в XML-отчёте `build/test-results/test/TEST-com.example.concurrent_booking_system.booking.service.PessimisticBookingIntegrationTest.xml`. HTML-отчёт: `build/reports/tests/test/index.html`.

В среде агента все 36 основных и 9 тестовых Java-файлов скомпилированы JDK 21. Через JUnit Platform 6.0.3 отдельно от Gradle прошли все 27 unit/MockMvc-тестов. Одна ошибка первоначальной настройки Mockito при повторном stub исправлена, после чего этот набор повторно прошёл полностью.

Полный Gradle-запуск не дошёл до сборки из-за read-only lock-файла в `~/.gradle`. Отдельный запуск PostgreSQL-класса остановился до тестовых методов: подключение к Docker socket запрещено (`SocketException: Operation not permitted`). **Успешность новых интеграционных тестов пока не подтверждена.** Сохранённые 30 успешных XML-отчётов относятся к предыдущему optimistic-шагу.

После успешного полного запуска рекомендуемый коммит:

```text
feat: add pessimistic booking with lock timeout handling
```

## Исправление независимости тестов

В последующем запуске владельца репозитория от 16 ноября 2026, 15:49 MSK, прошли **42 из 43 тестов**, включая ожидание commit/rollback, тайм-аут и восстановление настроек пула. Тест SQL-отката упал ещё на `ALTER TABLE`: глобальное ограничение `CHECK (status <> 'BOOKED')` проверяло ранее созданные места и обнаруживало уже существующие `BOOKED` строки.

В pessimistic- и optimistic-тестах ошибка исправлена: временное ограничение имеет вид `CHECK (id <> <currentSeatId> OR status <> 'BOOKED')`. Оно запрещает бронирование только текущего тестового места. Оба теста теперь специально создают другое забронированное место до добавления ограничения и проверяют его сохранность после отката. Это воспроизводит прежнюю проблему независимо от порядка запуска методов.

Код приложения и рабочие миграции не менялись. Исправленные тестовые классы скомпилированы JDK 21; повторное выполнение PostgreSQL-тестов после исправления ещё не подтверждено. Нужен новый полный запуск `./gradlew test --rerun-tasks`.
