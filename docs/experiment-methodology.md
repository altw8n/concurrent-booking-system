# Методика первого экспериментального пилота

## Статус и цель

Тема курсовой остаётся прежней: «Исследование методов управления конкурентным доступом к данным в высоконагруженной системе».

Этот этап готовит воспроизводимую цепочку: Java-тесты → отдельная БД → приложение → подготовленные данные → k6 → проверка зафиксированных данных → сохранённые результаты. Массовая серия и исследовательские выводы не выполняются автоматически. Метрики внутри приложения, повторы с измерением внутренних конфликтов и постоянный сбор Prometheus/Grafana относятся к следующим этапам.

Вспомогательный Python-скрипт решает две задачи: управление процессами/файлами и точный учёт исходных отсчётов. Стандартной библиотеки достаточно для subprocess, JSON, XML, CSV и percentile; pip-зависимости не вводятся. Делать это только в k6 означало бы смешивать генерацию нагрузки с управлением Docker/JVM, а Java-модуль для этой задачи увеличил бы объём прикладного проекта. Python не участвует в обработке HTTP-запросов Java-приложением. Node нужен только для тестов чистых JS-функций, без npm-пакетов.

Предварительное условие: полный набор Java-тестов успешен. Оркестратор выполняет Gradle и требует не менее 100 выполнений без падений/ошибок/пропусков, включая 16 тестов жизненного цикла. Старые 69 успешных отчётов не проходят эту проверку.

## Исследовательский вопрос и гипотезы

Как способ управления конкурентным доступом влияет на целостность, задержки, обработку запросов и технические конфликты при изменении числа клиентов и распределения запросов по местам?

До основной серии фиксируем проверяемые предположения:

1. У naive возможны несколько ACTIVE-бронирований одного места; для защищённых реализаций при рассматриваемой операции ожидается сохранение инварианта.
2. Увеличение конкуренции за одни строки изменяет задержки и распределение исходов; разные реализации могут реагировать по-разному.
3. Время ответа успешного бронирования и быстрого отказа «место занято» может различаться. Общий percentile без разделения исходов может скрывать это различие.

Это не требование получить конкретный результат. Пробный запуск проверяет пригодность стенда, а не доказывает эти гипотезы. Особенно нельзя требовать дублей naive в каждом HTTP-запуске: точный порядок чтений и записей здесь не навязывается.

## Переменные и условия

Независимые переменные:

- `strategy`: naive, optimistic, pessimistic, atomic, serializable.
- `vus`: число виртуальных клиентов с одним синхронным запросом на клиента в волне.
- `seats_per_wave`: число общих свободных мест, выделенных волне.

Клиент с индексом `c` выбирает место `c % seats_per_wave`. Поэтому при 10 клиентах и 10 местах у каждого своё место; при 10 клиентах и 2 местах каждая группа из пяти конкурирует за одно место; при одном месте все конкурируют вместе. При неделящемся числе клиентов размеры групп отличаются максимум на один запрос. Случайного выбора мест в пилоте нет.

Это заданное распределение, а не гарантия точного числа одновременных транзакций. k6 не ставит барьер внутри SQL. Фактическое перекрытие HTTP-интервалов оценивается отдельно; даже 100 активных клиентов могут ждать HikariCP и не означают 100 работающих транзакций PostgreSQL.

Контролируемые параметры: JDK 21, bootJar, PostgreSQL image ID и фактическая версия сервера, пул соединений, размер heap, timeout блокировок, timeout HTTP, окна волн, лимит опоздания старта, схема/Flyway, набор данных, отсутствие retries, логирование. Всё сохраняется в `config.json` и `manifest.json`.

Приложение запускается обычным `java -jar`, без перезагрузки между прогревом и измерением. Логирование Hibernate, включая SQL и сообщения об ожидаемых SQL-конфликтах, выключено, чтобы их вывод не добавлял разную стоимость записи логов стратегиям. Ограничения и настройки одинаковы для сравниваемых запусков. Версии k6/Docker/Compose, ОС, CPU и общий объём RAM также фиксируются. CPU, RAM и HikariCP во времени на этом этапе не измеряются.

В конфигурации по умолчанию используется `postgres:17` для совместимости с текущим проектом. Это изменяемый тег: сам по себе он не фиксирует patch-версию. Перед основной серией выбрать один конкретный tag/digest, сохранить его в конфигурации и сверять resolved image ID между запусками. Пилот записывает реальный ID, но не объявляет запуски с разными ID равнозначными.

## Почему выбраны свежие волны

Если отправлять запросы к одному месту минуту, оно почти сразу станет BOOKED. Остальное время будет измеряться преимущественно отказ для занятого места. Это отдельный полезный сценарий, но он не равен длительной конкуренции за свободный ресурс.

В пилоте все места создаются до нагрузки. Для каждого этапа и каждой волны выделяется непересекающийся набор. Во время измерений не выполняются отмена, reset, административный HTTP или создание новых мест. У клиентов сохраняются свои User ID, число которых равно `vus`.

Запуск имеет один локальный `per-vu-iterations` сценарий. Каждая VU выполняет `warmup_waves + measured_waves` итераций. Номер итерации VU задаёт волну, ID VU — клиента. Такая схема рассчитана на один локальный процесс k6; distributed/cloud запуск не поддерживается.

Волна `i` запланирована на `scenario.startTime + i * wave_interval_ms`. Клиент ждёт этой точки и делает один POST. Серверные и клиентские retry выключены. Прогрев и измерения разделяются по метке `phase` и по Seat ID. Три короткие волны прогрева в стандартном конфиге проверяют работоспособность цепочки; достаточный прогрев JVM для основной серии ещё предстоит подобрать.

Пилот требует, чтобы опоздание старта не превышало `max_start_lag_ms`, а запрос завершился до конца своего окна. Если условие нарушено, результат помечается недействительным, а исходные данные сохраняются. Границы волн не передвигаются молча вслед за медленными запросами. Также проверяется отсутствие фактического перекрытия соседних волн. Недействительный пилот может выявить реальную перегрузку: его нельзя скрывать или считать доказательством худшей стратегии. Исследование предельной нагрузки потребует отдельно согласованных правил работы с очередями, timeout и незавершёнными операциями.

Окна волн — планирование клиентских запросов, а не точный барьер БД. Допустимое опоздание не означает, что все запросы действительно пересеклись: в отчёте есть `dispatch_spread_ms` и `observed_peak_http_requests`.

## Показатели и определения

Для каждого запроса измеряется `booking_operation_ms`: время по клиентским часам вокруг синхронного `http.post`. Оно включает установление соединения и ожидание ответа; точность Date.now — миллисекунды. Это отличается от встроенного `http_req_duration`, который не включает начальные DNS/connection-времена. Внутренних повторов в этом пилоте нет.

Из исходных отсчётов рассчитываются p50/p95/p99 с линейной интерполяцией `(n - 1) * p`. Показывается число наблюдений `n`, все исходы вместе и каждый исход отдельно. При пяти успешных бронированиях нельзя интерпретировать p99 как устойчивую оценку хвоста распределения. Percentile итогового отчёта рассчитывается из клиентских отсчётов, а не из усреднения чужих percentiles.

Для волны длительность активного окна — от первого старта запроса до последнего завершения. В отчёте есть:

- `requests_per_wave_active_second = все запросы этапа / сумма активных окон волн в секундах`.
- `http_successes_per_wave_active_second = ответы 201 / тот же знаменатель`.
- `requests_per_elapsed_second_including_gaps = запросы этапа / время от первого старта до последнего завершения, включая межволновые паузы`.

Первый показатель характеризует обработку выбранных конечных всплесков, третий — фактическую скорость заданного темпа волн. Ни один сам по себе не доказывает предельную устойчивую пропускную способность сервера. Для неё потребуется другой согласованный сценарий постоянной нагрузки. HTTP-успех naive также не равен корректному бронированию — это оценивается проверкой целостности.

Исходы определяются по HTTP-статусу **и** JSON:

- `success`: 201 с положительным ID, ожидаемыми userId/seatId и статусом ACTIVE.
- `occupied`: 409 / SEAT_ALREADY_BOOKED — бизнес-отказ.
- `optimistic_conflict`: 409 / OPTIMISTIC_LOCK_CONFLICT, только optimistic.
- `serialization_failure`: 409 / SERIALIZATION_FAILURE, только serializable.
- `lock_timeout`: 503 / PESSIMISTIC_LOCK_TIMEOUT, только pessimistic.
- `transport_error`, `unexpected_response`: делают протокол неуспешным; не учитываются как обычное занятое место.

Счётчики внутренних DB-attempts/retries ещё не реализованы. Число технических конфликтов здесь выводится из окончательных HTTP-исходов при явно отключённых повторах. Нельзя переносить этот способ подсчёта на будущий запуск с retries, скрывающими часть конфликтов за успешным ответом.

## Проверка БД

После завершения k6 приложение останавливается, чтобы дождаться завершения запросов, включая запросы после клиентского timeout. Только затем состояние выгружается в JSON. Принудительный kill приложения или неуспешный k6 делают запуск недействительным. При ошибке оркестратор также пытается сохранить снимок для диагностики.

Для всех мест запуска и отдельно по этапам проверяются:

- `activeBookingsForSeat <= 1`; сохраняются нарушенные места и число лишних активных броней.
- FREE при отсутствии активных броней, BOOKED при их наличии.
- Каждый ответ 201 соответствует своей реально зафиксированной Booking, пользователю и месту.
- Нет лишних INSERT, которых нет среди успешных ответов, и повторного использования одного booking ID в нескольких успешных ответах.

Не требуется, чтобы каждое место непременно было забронировано: технические конфликты/тайм-ауты могут оставить ресурс свободным. Требуется согласованность фактических результатов и ответов.

`protocol_valid` означает полноту и корректность выполнения протокола. `correctness_passed` дополнительно требует инвариант и согласованность. `pilot_passed` допускает нарушение инварианта только для naive, сохраняя его в отчёте; другие ошибки учёта или статусов не оправдываются выбором naive.

## Изоляция и артефакты

Каждый запуск имеет уникальный Compose project и свежий volume отдельной PostgreSQL. Порты по умолчанию — БД 5433, приложение 8090; обычные 5432/8080 не используются. Схема создаётся штатным Flyway приложения. Данные засеиваются SQL через psql внутри экспериментального контейнера, без нового API и зависимостей Python для PostgreSQL.

Сохраняются эффективный конфиг, версии и SHA-256, точный seed.sql, соответствие пользователей/мест, raw-metrics.jsonl, summary.json, requests.csv, database.json, result.json и логи. При ошибке — failure.json. finally завершает приложение и удаляет только ресурсы уникального экспериментального проекта. Обычная база проекта не очищается.

Для основных запусков нужны закоммиченный код, зафиксированная конфигурация и одинаковые версии. Сейчас разрешён dirty tree для отладки пилота; это явно видно в manifest. Результаты не коммитятся автоматически и не подменяются успешными тестовыми fixtures.

## Что будет после успешного пилота

Сначала подтвердить один atomic-запуск: ожидаемое число запросов, корректная привязка данных, нулевые нарушения, сохранённые файлы и отсутствие пересечений волн. Затем проверить тот же сценарий с остальными стратегиями, подобрать длительность прогрева и размер серии.

Перед основной серией добавить минимальные внутренние метрики, проверить стоимость их сбора, зафиксировать окончательную матрицу и хотя бы три повторения важных конфигураций. Менять порядок стратегий, показывать разброс, не выбирать единственный «красивый» запуск. Отдельную серию с retries и длительную нагрузку оформлять отдельными протоколами.

Источники API инструментов: [k6 per-vu-iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/per-vu-iterations/), [k6 execution](https://grafana.com/docs/k6/latest/javascript-api/k6-execution/), [raw JSON](https://grafana.com/docs/k6/latest/results-output/real-time/json/), [custom summary](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/). Выбор протокола волн, критерии валидности и ограничения throughput — решения этого проекта, а не готовые гарантии инструмента.

## Проверено при реализации

Пройдены 10 Python-тестов учёта и 6 JavaScript-тестов распределения/классификации; Python и JavaScript проходят проверку синтаксиса, Compose-конфигурация валидна. В среде агента k6 не установлен; пробный оркестратор корректно остановился до нагрузки. Полный Gradle-запуск остановился на read-only lock-файле ~/.gradle. Настоящие k6/PostgreSQL-измерения этого этапа **не выполнены**, результатов сравнения стратегий пока нет.
