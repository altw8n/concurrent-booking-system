# Atomic conditional update: условное занятие места

## Что реализовано

Добавлен четвёртый вариант операции бронирования — `AtomicBookingStrategy`. Он использует то же правило `activeBookingsForSeat <= 1`, те же входные параметры, DTO и проверки пользователя/мероприятия, что и остальные реализации. Доступность места проверяется непосредственно в SQL-команде изменения.

Новых зависимостей, сущностей, таблиц и миграций нет. Текущий этап — корректность четвёртой реализации, а не измерение её производительности и не добавление SERIALIZABLE.

| Файл | Изменение |
|---|---|
| `booking/service/AtomicBookingStrategy.java` | Вся операция: проверки, условное занятие места, вставка бронирования. |
| `seat/repository/SeatRepository.java` | Нативный SQL `bookIfFree()`, возвращающий количество обновлённых строк. |
| `booking/service/BookingService.java` | Выбор `booking.strategy=atomic`; автоматические повторы optimistic к atomic не применяются. |
| `application.properties` | Комментарий с четвёртым доступным значением стратегии; default остаётся naive. |
| `AtomicBookingStrategyTest` | Проверки успешного результата и классификации отказов без БД. |
| `AtomicBookingIntegrationTest` | Восемь проверок SQL, конкуренции, отката и persistence context на PostgreSQL. |

Тест выбора стратегии дополнен двумя случаями. В optimistic-тесте обновлён конструктор `BookingService` — он теперь принимает четыре реализации. Контроллеры и обработчики HTTP-ошибок не менялись.

## Ключевой SQL

```sql
UPDATE seats
SET status = 'BOOKED'
WHERE id = :seatId
  AND event_id = :eventId
  AND status = 'FREE';
```

- `id` выбирает конкретную строку; первичный ключ ограничивает результат нулём или одной строкой.
- `event_id` не позволяет занять место другого мероприятия.
- `status = 'FREE'` проверяется самой БД в команде изменения.
- Результат `1` означает, что попытка заняла место. `0` означает, что условия не выполнены.

На успешном пути предварительный `SELECT seats` не нужен. Проверки существования пользователя и мероприятия сохраняются. После отказа выполняется чтение места, чтобы различить отсутствие/чужое мероприятие и уже занятое место.

Это атомарность одной SQL-команды. Вся бизнес-операция состоит из нескольких команд и всё равно нуждается в транзакции.

## Транзакция и порядок действий

`AtomicBookingStrategy.bookSeat()` объявлен с:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, isolation = Isolation.READ_COMMITTED)
```

`BookingService` вызывает Spring proxy стратегии, а не создаёт её вручную. Proxy начинает отдельную транзакцию, выполняет метод и завершает транзакцию до возврата результата вызывающему коду.

Приблизительная последовательность SQL:

```sql
BEGIN;
-- READ COMMITTED задаётся через Spring/JDBC.
SELECT COUNT(*) FROM events WHERE id = :eventId;
SELECT COUNT(*) FROM users WHERE id = :userId;

UPDATE seats
SET status = 'BOOKED'
WHERE id = :seatId AND event_id = :eventId AND status = 'FREE';

-- Только если обновлена одна строка:
INSERT INTO bookings (...) VALUES (...);
COMMIT;
```

Многоточия пояснительные, это не готовый SQL-скрипт. `BEGIN`/`COMMIT` показывают границы транзакции; их не пишет контроллер. Все команды используют одно транзакционное JDBC-соединение.

После успешного `UPDATE` создаётся `Booking` со статусом `ACTIVE`. Hibernate выполняет `INSERT` при `save()`, поскольку нужен IDENTITY-идентификатор. Возвращаемый DTO получает этот ID. Успешный ответ выходит из proxy после commit.

Если вставка бронирования или фиксация транзакции завершается runtime-ошибкой, Spring откатывает транзакцию. Уже выполненный `UPDATE` тогда тоже отменяется: место остаётся `FREE`. Выполнение SQL не означает, что изменения уже зафиксированы.

У этой реализации порядок отличается от naive: сначала занять место, затем создать бронирование. Это часть механизма при сохранении той же бизнес-операции и итоговых гарантий.

## Что происходит при конкуренции

Два запроса могут одновременно отправить `UPDATE` для одного места. PostgreSQL блокирует изменяемую строку, поэтому конкурент может ждать завершения первой транзакции.

После commit первого запроса второй при READ COMMITTED повторно проверяет условие на изменённой строке. Она уже `BOOKED`, поэтому второй `UPDATE` возвращает 0 строк. Если первый запрос откатился, второй может занять место, оставшееся свободным.

Таким образом, atomic conditional update не означает отсутствие блокировок или ожиданий. Отдельного `SELECT FOR UPDATE` здесь нет; блокировка возникает при самом изменении и удерживается до завершения транзакции.

У atomic нет отдельного `lock_timeout` или механизма retry. Настройка `booking.pessimistic.lock-timeout-ms` действует только в pessimistic-стратегии. При будущих измерениях нужно явно фиксировать пределы ожидания и остальные условия всех вариантов; отсутствие отдельного тайм-аута не является гарантией мгновенного ответа.

## JPA/Hibernate и устаревшие сущности

Метод репозитория использует:

```java
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query(value = "...", nativeQuery = true)
```

`nativeQuery=true` означает, что текст написан на SQL с именами таблиц и столбцов PostgreSQL. `@Modifying` сообщает Spring Data JPA, что нужно выполнить изменение и вернуть число строк, а не получить список сущностей.

Прямое обновление БД не переписывает поля уже загруженного Java-объекта `Seat`. Поэтому:

1. `flushAutomatically` отправляет возможные ожидающие JPA-изменения перед SQL.
2. Выполняется условный `UPDATE`.
3. `clearAutomatically` очищает весь persistence context — старые объекты становятся detached.

Очистка не меняет поля старого Java-объекта. Повторное чтение после неё загружает новое состояние из БД. В atomic-операции `Booking` создаётся после очистки; несохранённых сущностей, которые нужно было бы продолжать использовать, в этот момент нет. Сам `Seat` через dirty checking не изменяется, `markBooked()` и `save(seat)` здесь не вызываются.

Нативный SQL не использует `@Version` и не увеличивает столбец версии. Существующие naive и pessimistic также не получают проверку версии от этого метода. Optimistic продолжает использовать отдельное версионируемое отображение.

## Ошибки и область гарантий

При результате 0 стратегия читает место по ID и проверяет мероприятие:

- нет подходящего места — `SeatNotFoundException`, HTTP 404;
- место относится к мероприятию — `SeatAlreadyBookedException`, HTTP 409.

Это соответствует текущей модели, где конкурентные операции занимают места, а отмена, удаление мест и временные удержания ещё не реализованы. Когда появится конкурентная отмена, классификацию после нулевого UPDATE нужно отдельно проверить: между UPDATE и диагностическим чтением состояние может снова измениться.

При положительном результате создаётся одно бронирование. При отказе новое бронирование не создаётся. Ошибки пользователя и мероприятия обрабатываются прежними исключениями до попытки занятия места.

Гарантия относится к корректному исходному состоянию и операциям записи, соблюдающим выбранный протокол. Прямые вставки Booking или одновременный запуск naive над теми же местами обходят защиту. Дубликаты, оставшиеся от naive-эксперимента, не исправляются. Каждый запуск исследования использует одну стратегию и свежие данные.

## Проверки

Восемь PostgreSQL-тестов проверяют:

1. Успешное бронирование и последовательный отказ второму пользователю.
2. Четыре конкурентные попытки занять одно место: один победитель, три отказа, ровно одно активное бронирование.
3. Два разных места могут быть изменены до фиксации любой из двух транзакций.
4. Второй UPDATE действительно ждёт, затем после commit первого повторно проверяет FREE и отказывает.
5. После rollback первого UPDATE ожидающий второй успешно занимает место.
6. Ошибка INSERT Booking откатывает уже выполненное занятие места. Ограничение для ошибки привязано только к текущему месту; предварительно создаётся другое бронирование для независимости от порядка тестов.
7. Bulk update очищает устаревшую управляемую сущность; повторное чтение получает BOOKED. Репозиторная проверка выполняется в отдельной транзакции с принудительным rollback, чтобы не оставить место без бронирования.
8. Невалидный запрос, отсутствующие сущности и чужое мероприятие корректно различаются и не оставляют частичных записей.

Для гонки четырёх запросов используется барьер **перед** UPDATE. Для разных мест — барьер **после** двух успешных UPDATE. Для ожидания одного места — latch, удерживающий первую транзакцию, и наблюдение `pg_stat_activity` / `pg_blocking_pids()`. Эти вмешательства находятся только в тестах и не используются для измерения производительности.

В тестовом контексте пул из шести соединений: четыре для конкурентов и запас для наблюдения/подготовки. Это настройка correctness-теста, не будущего нагрузочного эксперимента. На тестовом классе нет внешней `@Transactional`: проверяется реальное завершение транзакций сервиса.

Полный набор теперь содержит **56 тестов в 11 классах**: 32 unit/MockMvc и 24 PostgreSQL-теста.


