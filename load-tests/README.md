# Пробный эксперимент k6

Это первый сквозной стенд, не готовые результаты курсовой. Методика и ограничения: [experiment-methodology.md](../docs/experiment-methodology.md).

Нужны Linux, JDK 21, Docker с Compose, Python 3 и бинарный `k6` в PATH. Новых Python/npm-зависимостей нет. Установка k6: [официальная инструкция](https://grafana.com/docs/k6/latest/set-up/install-k6/). Node нужен только для самостоятельных тестов JavaScript-функций, не для создания нагрузки.

Проверить инструменты:

```bash
k6 version
docker version
docker compose version
/usr/lib/jvm/java-21-openjdk/bin/java -version
```

Из корня репозитория запустить **один** пилот:

```bash
python experiments/run_pilot.py --strategy atomic
```

Оркестратор сам выполняет `./gradlew --no-daemon test bootJar` и проверяет отчёты: минимум 100 успешных Java-тестов, включая все 16 lifecycle-проверок, без пропусков. До этого нагрузка не начинается. Параметра обхода проверки нет. Путь JDK в другой системе задаётся через `--java`.

Затем поднимается отдельная PostgreSQL на `127.0.0.1:5433` и отдельный экземпляр приложения на `127.0.0.1:8090`. Обычная Compose-БД на 5432 не используется. Оркестратор готовит данные, запускает k6, завершает приложение и выгружает состояние БД. В конце удаляет только контейнеры и volume собственного уникального Compose-проекта. Все файлы результата остаются на диске. Одновременно выполнять два пилота на одних портах нельзя; при необходимости есть `--app-port` и `--db-port`.

По умолчанию: 10 клиентов, 2 места в волне, 3 волны прогрева и 5 измеряемых волн. Каждый клиент делает ровно один запрос в каждой волне, без клиентского retry. Серверные retry принудительно отключены. Паузы между волнами не входят в latency запроса; для throughput отчёт явно показывает разные знаменатели.

После первого успешного пилота можно проверить тот же протокол с другой стратегией:

```bash
python experiments/run_pilot.py --strategy optimistic
```

Для другой конкуренции за данные менять `--seats-per-wave` при одинаковом `--vus`:

```bash
python experiments/run_pilot.py --strategy atomic --vus 10 --seats-per-wave 10
python experiments/run_pilot.py --strategy atomic --vus 10 --seats-per-wave 1
```

Эти команды — примеры отдельных запусков, не автоматическое выполнение всей матрицы. Сначала достаточно одного успешного atomic-пилота.

Конфигурация остальных параметров: `experiments/configs/pilot.json`. Не сокращать интервал так, чтобы он не вмещал timeout запроса и допустимое опоздание старта. Для пробного стенда установлен предел 100 клиентов; выбор диапазона основной серии делается после оценки генератора нагрузки.

Результаты появляются в `experiments/raw-results/<run-id>/`. В первую очередь смотреть:

- `manifest.json` — версии, параметры JVM, Git, SHA-256 приложения и скриптов, тестовая проверка, завершение и cleanup.
- `result.json` — валидность протокола, исходы, latency, окна волн, фактическое перекрытие HTTP-запросов и целостность.
- `requests.csv` — строки отдельных запросов с HTTP-статусом, API-кодом ошибки, исходом и ID успешной брони, восстановленные из исходных k6-метрик.
- `database.json` — сохранённые места и бронирования после остановки приложения.
- `failure.json` — причина незавершённого запуска, если есть.

`pilot_passed=true` означает, что пробный протокол прошёл проверки; это не доказательство достаточности прогрева или статистической надёжности. Для naive запуск может быть валидным при `correctness_passed=false`: дубли ACTIVE — измеряемый результат. Отсутствие дублей в одном HTTP-пилоте также допустимо и не доказывает безопасность naive.

Код возврата 0 означает успешный пилот и cleanup. Код 1 требует прочитать артефакты; повторять такой запуск как будто он успешен нельзя. После SIGKILL или выключения компьютера Python не сможет выполнить finally: имя уникального проекта сохранено в `manifest.json`, чтобы отдельно удалить его через тот же Compose-файл.

Локальные проверки скриптов без Docker/k6:

```bash
python -m unittest discover -s experiments/tests -v
node load-tests/pilot-model.test.mjs
docker compose --file experiments/docker-compose.yml config --quiet
```

Это тесты распределения данных, классификации ответов и корректности расчётов. Они не заменяют запуск настоящего k6 и PostgreSQL.

Сырые результаты исключены из Git, но должны сохраняться для курсовой. Основные серии следует архивировать отдельно; `.gitignore` не является резервным копированием.

## Автоматический сбор существующих результатов

Из корня репозитория:

```bash
python experiments/collect_results.py
```

Это офлайн-обработка: Docker, k6, Java и новые измерения не запускаются. Нужен только Python 3, без дополнительных пакетов. Исходные результаты не изменяются.

В `experiments/processed-results/` создаются три файла:

- `runs.csv` — одна строка на запуск: параметры, статус, все исходы, доли успехов и технических конфликтов, latency, показатели обработки волн и нарушения инварианта. CSV с UTF-8 BOM можно открыть в LibreOffice Calc; разделитель — запятая, десятичный разделитель — точка. Поле `source` указывает на исходную папку.
- `groups.json` — группы одинаковых условий, количество учтённых/исключённых запусков, недостающие и лишние повторы. Для метрик отдельных запусков рассчитываются медиана, минимум и максимум; также сохраняется latency по исходам и число наблюдений.
- `summary.md` — краткая таблица повторов и список замечаний, удобные для чтения в IDE.

Собрать результаты из другой серии или сменить папку отчётов:

```bash
python experiments/collect_results.py \
  --input experiments/raw-results \
  --output experiments/processed-results \
  --expected-repeats 3
```

Повторный запуск обновляет эти три отчёта по текущим исходным файлам. Входная и выходная папки должны быть отдельными, не вложенными друг в друга. Для независимых серий рекомендуется использовать разные входные папки.

### Как читать таблицу

Основные параметры — `strategy`, `vus`, `seats_per_wave`, `warmup_waves`, `measured_waves`. Показатели `success`, `occupied`, `optimistic_conflict`, `serialization_failure`, `lock_timeout`, `p50_ms`, `p95_ms`, `p99_ms`, `extra_active_bookings` относятся только к **измеряемой** части. `overall_*`, `invariant_holds` и флаги исходного результата учитывают также прогрев. `technical_conflict_rate` и `http_success_rate` — доли от 0 до 1, не проценты; технические конфликты включают optimistic/serialization/lock timeout и считаются по окончательным исходам при отключённых retries.

`included=True` означает, что запуск подходит для описательной сводки по сохранённым флагам протокола, согласованности счётчиков и завершения/cleanup. `status=naive_violation` сохраняет нарушение naive как наблюдение. Ошибка защищённой стратегии, некорректный протокол, отсутствующий результат или повреждённый JSON остаются в CSV с `included=False` и причиной в `issues`. Они не засчитываются как повтор, но не удаляются из отчётов. Скрипт читает сохранённый результат; повторную проверку SQL и исходных метрик он не выполняет.

### Какие запуски объединяются

Один `condition_id` соответствует одинаковым параметрам конфигурации (кроме стратегии и адреса приложения), Git-коммиту, хешам JAR/сценариев, версиям инструментов, PostgreSQL image ID и сохранённым сведениям о машине. Внутри условий каждая стратегия имеет свою группу повторов. Разные волны, пул, прогрев, версии кода/образа и другие зафиксированные условия не смешиваются. Даже при одинаковом JAR разные Git-коммиты консервативно разделяются. Полное описание условий сохраняется в `groups.json`.

Изменённое рабочее дерево отмечается предупреждением, но пилоты не исключаются автоматически: хеши измеряемого артефакта и сценариев сохраняются. Для основной серии всё равно следует зафиксировать код. Совпадение метаданных не доказывает одинаковую фоновую нагрузку компьютера.

`--expected-repeats 3` задаёт цель для **уже обнаруженных условий** и всех пяти стратегий. Он не запускает повторы, не выбирает лучшие три из лишних и не проверяет полноту всей будущей матрицы: сценарий, для которого нет ни одного запуска, ещё неизвестен сборщику. Исходные run ID сохраняются; номера повторов по времени не придумываются.

Медиана трёх p95 — сводка трёх отдельных оценок p95, а не p95 объединённых запросов. Доверительные интервалы и графики на этом этапе не рассчитываются. Показатели активных окон волн не следует называть максимальной устойчивой пропускной способностью. Малое число успешных запросов делает хвостовые процентили нестабильными.

Код возврата сборщика: `0` — все обнаруженные запуски прочитаны и учтены (это не подтверждение наличия трёх повторов); `1` — нет запусков или есть исключённые/непрочитанные запуски, отчёты всё равно записаны; `2` — ошибка аргументов. Если цель — три повтора, наличие недостающих нужно смотреть в `summary.md` / `groups.json`.

Проверить обработку без нагрузки:

```bash
python -m unittest discover -s experiments/tests -v
```

Производные отчёты также исключены из Git. Для архива исследования сохраняйте их вместе с исходными папками.
